前回のEpisodeでは、okozeを始めた理由と、このプロジェクトを通して考えてみたいことを書きました。

今回は、実際にokozeを作るための開発環境を決めます。

開発環境は、最初から複雑にする必要はありません。

むしろ、最初はできるだけシンプルにしたいと思っています。

また、今の段階で決めなくてもよいこともあります。

最初からすべてを決めてしまうのではなく、**開発を始めるために必要なことだけを決め、必要になったときに改めて判断する**ことにします。

## Webアプリケーションか、スタンドアロンアプリケーションか

大きく分けると、次の2つの方法があります。

* Webアプリケーション
* スタンドアロンアプリケーション

スタンドアロンアプリケーションなら、OSに直接アクセスできますし、Webプラットフォームによる制約も避けることができます。

一方、今回のokozeにはWebアプリケーションにも魅力があります。

複数のOS向けに別々のバージョンを用意しなくても、多くの環境で動かせる可能性があります。

スマートフォンやタブレットでも使えます。

必要になれば、後からスタンドアロンアプリケーションとしてパッケージすることもできます。

そして、この連載にとって特に重要な理由があります。

Webアプリケーションなら、**GitHub Pagesでそのまま公開できます。**

つまり、okozeの開発途中の各段階を、**Live Demo**として公開できる可能性があります。

読者はソフトウェアをインストールしなくても、その時点のokozeを実際に動かしてみることができます。

開発過程を公開する連載として、これは大きなメリットだと思います。

もちろん、Webアプリケーションにも欠点があります。

Webアプリケーションは一つの技術だけでできているわけではありません。

ブラウザ、JavaScriptやTypeScript、Web API、さらに必要に応じてさまざまなツールやライブラリを組み合わせることになります。

それでも、今回のプロジェクトではメリットの方が大きいと判断しました。

**okozeはWebアプリケーションとして開発することにします。**

## 開発マシン

開発には、今持っているマシンを使います。

**Mac mini M4**です。

特別な理由があるわけではありません。

単に、私が現在使っているマシンだからです。

okozeそのものは、このハードウェアに依存しないようにします。

そのため、他の開発者とまったく同じ開発環境を用意しようとは考えていません。

## プログラミング言語

最初は**JavaScript**を使います。

小さなWebアプリケーションのプロトタイプを作るには、JavaScriptが一番素直な選択だと思います。

okozeに何が必要なのかまだよく分かっていない段階で、余計な複雑さを持ち込みたくありません。

ただし、プログラムが大きくなれば、いずれTypeScriptが役に立つだろうとも考えています。

現在の予定は、

> **JavaScriptで始めて、プログラムが大きくなりすぎる前にTypeScriptへ移行する。**

です。

ただし、これはあくまで予定です。

実際に移行してみて大変すぎるようなら、もっと早い段階でTypeScriptに移行するかもしれません。

逆に、プログラムが小さいままでJavaScriptで十分なら、無理に移行する必要もありません。

実際に開発してみて判断します。

## IDE

IDEには**Visual Studio Code**を使います。

Web開発で広く使われていますし、JavaScript、TypeScriptのサポートも充実しています。

Visual Studio Codeそのものの使い方については、ここではあまり詳しく説明しません。

okozeの開発に関係する部分を中心に記録していきます。

ローカルの開発サーバーには、Visual Studio Codeの**Live Server**拡張機能を使います。

簡単なWebサーバーを起動でき、ファイルを変更するとブラウザを自動的に再読み込みしてくれます。

今の段階では、もっと高度な開発サーバーは必要ありません。

## ブラウザ

開発とテストには、**Chromium系のブラウザ**を使います。

ChromiumにはDeveloper Toolsがあり、アプリケーションの調査、ログやエラーの確認、プログラムの動作確認などに便利です。

ただし、okozeそのものはChromium固有の機能に依存しないようにします。

そのため、この連載を読んで同じように試す場合も、他のモダンブラウザを使えるようにするつもりです。

## グラフィックス

okozeの主要なグラフィックス部分は、最初はブラウザの**Canvas API**を使います。

最初のプロトタイプでは、グラフィックスライブラリを導入せず、Canvasを直接使ってみます。

Canvasは比較的低レベルのAPIです。

しかし、現時点では、okozeのグラフィックス部分にどこまでの機能が必要になるのか、まだ分かっていません。

今の段階でグラフィックスライブラリを選ぶこともできます。

でも、それは必要なものが分かっていないうちに決めてしまうことになります。

そこで、まずはCanvasを直接使って小さな動くアプリケーションを作ってみます。

okozeをある程度実装して必要な機能が分かってきたところで、利用できるグラフィックスライブラリを調べ、比較してみたいと思います。

特に、グラフィックス要素の数が増えたときの性能については、実際に測定してみたいと思っています。

例えば、

* Canvas APIを直接使う
* グラフィックスライブラリを使う
* SVGを使う

といった方法を比較することになるかもしれません。

具体的に何を比較するかは、そのときに決めます。

今は、

> **まずはシンプルに作り、必要になったときに、より高機能なグラフィックス環境を選ぶ。**

という方針にします。

これも、今の段階では**あえて決めないことにしたもの**の一つです。

## バージョン管理

ソースコードは**Git**で管理し、**GitHub**に置きます。

GitHubのリポジトリを、単に最新のソースコードを置く場所として使うだけではなく、開発過程の記録としても使いたいと思っています。

okozeの開発で一つの段階が完成したら、Gitのtagを付けます。

例えば、

```text
episode-001
episode-002
episode-003
````

というtagです。

GitHub Pagesで公開するLive Demoも、これらの段階に対応させます。

そうすると、

* その時点のokozeがどんなものだったか
* そのバージョンを作ったソースコードは何だったか

の両方を確認できます。

つまりGitHubのリポジトリは、単なる最新ソースコードの保管場所ではありません。

**開発記録そのものの一部**になります。

## AIを使ってプログラミングする

コードを書くときには、**AIを積極的に使います。**

これはEpisode-001で書いた、この連載の実験の重要な部分でもあります。

現在のAIは、かなりの量のコードを生成できます。

しかし、AIがコードを書いてくれるからといって、要求仕様や設計、テスト、そして開発者自身の判断が不要になるわけではありません。

このプロジェクトでは、AIを**プログラミングのパートナー**として使います。

何を作りたいのかは私が決めます。

その実装についてAIに相談し、生成されたコードを調べ、実際に動かし、テストし、次に何をするかを決めます。

AIを実際の開発でどのように使ったのかも、この開発記録の一部にしていきます。

AIを使った開発で、どのような方法が一番うまくいくのかは、まだ分かりません。

それも、このプロジェクトを通して試してみたいことの一つです。

## 私のWeb開発経験について

ここで一つ、書いておいた方がよいことがあります。

私の主な専門分野は、**CADと幾何処理**です。

長い間ソフトウェア開発をしてきましたが、Webアプリケーションの開発経験はほぼありません。

つまり、プログラミングやグラフィックスについてはそれなりに経験がありますが、Webプラットフォームについては、それほど詳しくありません。

そのため、この連載で書くWeb開発についての説明には、驚くほど基本的なものや、少し素朴なものが出てくるかもしれません。

最初から使う技術をすべて知っているわけではありません。

**作りたいものが先にあって、必要になったことを、その都度学んでいく。**

そのようにしてokozeを作っていきます。

## 開発環境

最初の開発環境をまとめると、次のようになります。

| 目的 | 使用するもの |
| --------- | ----------------------- |
| 開発マシン | Mac mini M4 |
| IDE | Visual Studio Code |
| ブラウザ | Chromium系ブラウザ |
| 開発サーバー | Live Server |
| プログラミング言語 | JavaScript → TypeScript |
| グラフィックス | Canvas API |
| バージョン管理 | Git / GitHub |
| Live Demo | GitHub Pages |
| コーディング支援 | AI |

意図的に、小さな環境にしています。

すでに決めたこともあります。

一時的に決めているだけのこともあります。

そして、まだ決めていないこともあります。

それでよいと思っています。

アプリケーションを作り始める前に、開発環境の設計に時間をかけすぎたくありません。

まずはこの環境を作って、実際にコードを書いてみます。

そして、実際に開発してみることで、今決めたことがうまくいくのかどうかを確かめていきます。

次回は、この開発環境を実際に構築します。
